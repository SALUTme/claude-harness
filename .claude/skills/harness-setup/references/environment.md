# Фаза 7b. Окружение

Цель: тесты проекта одинаково запускаются в облачной сессии, на Mac и в CI. Агент не тратит сессию на ручную установку зависимостей, а сломанный код виден даже тогда, когда агент не работает.

Исходные данные: измерение 11 «Окружения» из `docs/BRIEF.md`, стек из PRD, `HARNESS_TEST_CMD` из `.claude/harness.env`.

## Три слоя

| Слой | Где живёт | Когда работает | Что туда класть |
|---|---|---|---|
| Облачное окружение | Настройки облака на claude.ai/code: скрипт установки, переменные, доступ к сети | Первая сессия в окружении, дальше из кэша | Системные пакеты и инструменты, которых нет в облаке |
| Подготовка проекта | `.claude/hooks/project-setup.sh`, запускает хук `env-setup` | Начало каждой облачной сессии, на Mac по включению, первый шаг CI | Зависимости проекта и запуск служб |
| CI | `.github/workflows/ci.yml` | Каждый push в любую ветку | Та же подготовка и тот же `HARNESS_TEST_CMD` |

## 1. Подготовка проекта

1. Скопируй `<папка скилла>/templates/project-setup.sh` правкой файла в `.claude/hooks/project-setup.sh`. Пользователь подтверждает правку.
2. Оставь только команды стека проекта. Установка зависимостей идёт по lock-файлу и пропускается, если lock-файл не менялся.
3. Службы для тестов, например PostgreSQL, Redis или `docker compose`, запускай только при `HARNESS_CONTEXT=cloud`. На Mac службы запускает человек, в CI их описывает блок `services`.
4. Никаких секретов и боевых данных. Тестовые пароли допустимы только для локальных служб в облаке и CI.
5. Проверь запуском и покажи итог пользователю. В облаке через хук, на Mac напрямую:
   ```bash
   bash .claude/hooks/env-setup.sh; tail -n 20 .harness/runtime/env-setup.log
   ```
   ```bash
   HARNESS_CONTEXT=local bash .claude/hooks/project-setup.sh
   ```
6. Повторный запуск должен занимать секунды. Если нет, найди шаг, который не пропускается.

Почему файл лежит в `.claude/hooks/`: хук запускает его автоматически в начале сессии, мимо проверок опасных команд. Поэтому менять его можно только правкой с подтверждением человека, а через терминал хуки это запрещают.

Этого недостаточно для полной защиты: менеджеры пакетов читают файлы проекта, которые агент меняет без подтверждения. `npm ci` выполняет скрипты из `package.json`, `docker compose` читает `docker-compose.yml`. Поэтому:
1. В облаке подготовка запускается всегда: машина одноразовая и отделена от твоего компьютера.
2. На Mac подготовка запускается автоматически, только если человек включил `HARNESS_ENV_SETUP_LOCAL=1` в `.claude/harness.env`. Иначе агент предлагает запустить её вручную, и команда проходит обычные проверки.
3. В скрипте используй установку строго по lock-файлу и без скриптов пакетов, где это возможно: `npm ci --ignore-scripts`. Не вызывай `npm run`, `make` и другие цели, которые агент может переписать.
4. Подготовка ограничена 540 секундами. Долгие установки переноси в скрипт облачного окружения, он кэшируется.
5. Переменные окружения из скрипта, например `PATH` или `VIRTUAL_ENV`, в сессию сами не попадают. Допиши их в файл `$CLAUDE_ENV_FILE`, если он задан: `[ -n "${CLAUDE_ENV_FILE:-}" ] && echo 'export PATH="$HOME/.local/bin:$PATH"' >> "$CLAUDE_ENV_FILE"`.

## 2. Облачное окружение

В облаке уже есть Python, Node.js, Go, Rust, Java, Ruby, PHP, Docker, PostgreSQL, Redis, git, gh и jq. Плагины oh-my-claudecode и Codex ставятся сами из `.claude/settings.json`. Отдельно настраивать окружение нужно, только если чего-то не хватает.

Если не хватает, объясни пользователю по шагам, что сделать самому на claude.ai/code:
1. Открыть выбор облачного окружения и настройки окружения.
2. В **Setup script** вставить установку недостающего. Скрипт должен завершаться с кодом 0 и укладываться в пять минут. Результат кэшируется примерно на неделю.
3. Если тестам нужен сторонний домен, в **Network access** выбрать **Custom**, отметить список по умолчанию и добавить домен.
4. Ключи тестовых песочниц на планах Pro и Max добавлять как **API credentials**: агент их не видит. Обычные переменные окружения видит любой, кто пользуется окружением.

Текст скрипта и список доменов запиши в `docs/HARNESS.md`, раздел «Окружение». Настройки облака не хранятся в репозитории, и без этой записи их не восстановить.

Codex в облаке не настраивается: он работает по подписке через вход в браузере. Ревью Codex выполняется в сессиях на Mac, подробности в `references/verification.md`.

## 3. CI

1. Скопируй `<папка скилла>/templates/ci.yml` в `.github/workflows/ci.yml`. Пользователь подтверждает правку.
2. Раскомментируй установку языка нужной версии и, если нужно, блок `services`.
3. Закоммить и отправь ветку. Если GitHub отклонил push из-за прав на workflows, дай пользователю путь и содержимое файла, чтобы он создал файл в веб-редакторе GitHub.
4. Дождись результата для своего коммита:
   ```bash
   gh run list --commit "$(git rev-parse HEAD)" --limit 1 --json databaseId,status,conclusion
   ```
   Если запуска для этого коммита ещё нет, CI не закончен, а не зелёный: проверь снова через минуту. Когда запуск появился, дождись его: `gh run watch ID --exit-status`, где ID это `databaseId`.
   Красный CI значит, что фаза не пройдена. Причину смотри командой `gh run view --log-failed`.
5. Предложи пользователю включить на GitHub защиту ветки main с обязательной проверкой CI. Это делает человек в настройках репозитория: Settings, Branches.

## 4. Тестовый стенд

Нужен, когда результат надо смотреть глазами: сайт, веб-приложение, API для мобильного клиента. Для библиотек, CLI и ботов без интерфейса обычно не нужен. Решение за пользователем, спроси через `AskUserQuestion`.

| Проект | Варианты | Как подключается |
|---|---|---|
| Фронтенд, статический сайт, Next.js | Vercel, Netlify, Cloudflare Pages | Превью на каждый pull request |
| Бэкенд, API, бот | Railway, Render, Fly.io | Отдельный сервис staging из ветки или pull request |
| Мобильное приложение | Expo EAS Update, TestFlight | Сборка для тестировщиков |

Правила:
1. Аккаунт у провайдера, подключение GitHub и переменные окружения стенда настраивает человек в интерфейсе провайдера. Ты даёшь пошаговую инструкцию.
2. Ты пишешь только файлы конфигурации в репозитории, например `vercel.json`, и документацию.
3. Стенд работает с тестовыми данными и тестовыми ключами, никогда с боевой базой.
4. Адрес стенда или шаблон адреса превью запиши в `docs/HARNESS.md` и в раздел «Команды» CLAUDE.md.

## Ворота

1. `.claude/hooks/project-setup.sh` есть и отработал без ошибки, либо фаза подготовки записана как ненужная с причиной.
2. CI прошёл хотя бы один раз зелёным, либо пользователь отказался от CI и это записано в `docs/DECISIONS.md`.
3. Решение по тестовому стенду записано: адрес или отказ с причиной.
4. Раздел «Окружение» в `docs/HARNESS.md` заполнен.
