# Фаза 0. Git и GitHub

Проект без коммитов и без GitHub живёт в одном экземпляре на одной машине: нет истории для отката, нет резервной копии, ворота обвязки и CI не работают. Этот шаг закрывает это до начала работы. Каждое действие на GitHub выполняется только после явного согласия пользователя через `AskUserQuestion`.

## 1. Имя и почта для коммитов

```bash
git config user.name; git config user.email
```
Если почта пустая, коммит упадёт. Предложи анонимный адрес GitHub: он не раскрывает личную почту в истории.
```bash
gh api user --jq '"\(.id)+\(.login)@users.noreply.github.com"'
```
Запиши его в настройки этого репозитория, глобальные не трогай: `git config user.email АДРЕС` и `git config user.name "ИМЯ"`. Имя спроси у пользователя.

## 2. Секреты не должны попасть в коммит

Сделай до первого коммита и до первого push.

1. `.gitignore` должен закрывать файлы с секретами и рабочие данные: `.env`, `.env.*.local`, `.envrc`, папки вроде `.secrets/`, ключи `*.pem`, `*.key`, выгрузки и логи. Посмотри, что в проекте реально есть, и предложи недостающие строки.
2. Посмотри, что попадёт в коммит: `git add -A --dry-run`. Покажи пользователю список, если он короткий, или сводку по папкам, если длинный.
3. Проверь содержимое этих файлов на похожее на секреты:
   ```bash
   . .claude/hooks/_harness_lib.sh; git -c core.quotePath=false add -A --dry-run | sed -E "s/^add '(.*)'$/\1/" | while IFS= read -r f; do [ -f "$f" ] || continue; k=$(harness_secret_kind "$(cat "$f")") && echo "$f: $k"; done
   ```
   Найденное не коммить. Вынеси секрет в `.env` или в папку из `.gitignore` и предложи человеку сменить ключ, если он уже где-то засветился.
4. Файлы больше 50 МБ GitHub не примет: `find . -path ./.git -prune -o -type f -size +50M -print`.

## 3. Первый коммит

Если коммитов нет, покажи итог проверки из шага 2 и с согласия пользователя сделай первый коммит всего проекта. Ветку назови `main`, если пользователь не против: `git branch -M main`.

## 4. Приватный репозиторий на GitHub

Если `git remote get-url origin` пустой:

1. Объясни одной-двумя фразами, зачем: резервная копия вне этой машины, история, CI, PR с обновлениями обвязки, работа из облака и с телефона.
2. Владелец. Личный аккаунт: `gh api user --jq .login`. Организации: `gh api user/orgs --jq '.[].login'`. Спроси, где создать. Рабочие проекты обычно живут в организации.
3. Название: по папке проекта, латиницей через дефис. Проверь, что свободно: `gh repo view ВЛАДЕЛЕЦ/НАЗВАНИЕ`.
4. Покажи владельца, название и приватность и получи согласие. Затем:
   ```bash
   gh repo create ВЛАДЕЛЕЦ/НАЗВАНИЕ --private --source . --remote origin --push
   ```
5. Разрешение для PR с обновлениями обвязки, с согласия пользователя:
   ```bash
   p=$(gh api repos/ВЛАДЕЛЕЦ/НАЗВАНИЕ/actions/permissions/workflow --jq .default_workflow_permissions) && gh api -X PUT repos/ВЛАДЕЛЕЦ/НАЗВАНИЕ/actions/permissions/workflow -f default_workflow_permissions="$p" -F can_approve_pull_request_reviews=true
   ```
   В организации эту галочку может запрещать настройка самой организации. Тогда скажи пользователю, где её включить: настройки организации, Actions, General.
6. Дай ссылку на репозиторий. Если проект создан из основы и `harness-update.yml` есть, обновления обвязки начнут приходить PR.

Если `gh` не вошёл в GitHub, предложи пользователю выполнить `gh auth login`. Вход выполняет только сам пользователь.

## Ворота

Есть хотя бы один коммит. Есть `origin`, либо в `.harness/bootstrap-state.json` записан отказ от GitHub с причиной. Проверка на секреты сделана, её итог показан пользователю.
